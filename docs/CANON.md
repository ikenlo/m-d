# Канон MDS Connect v0.3.0 (затверджено директором 11.11.2026)

Цей файл разом із [FINANCE.md](FINANCE.md) — **єдине джерело правди** щодо бізнес-правил.
Він має пріоритет над кодом, коментарями, старими документами (`docs/ARCHIVE/`) і аудитом (`audit/`).
Код, що суперечить канону, треба змінити (фаза 2 плану), а не канон.
Стан відповідності коду — `audit/21_CANON_COMPLIANCE.md` (знімок на 11.11.2026, не оновлюється).

- Фінанси (гроші, формула поділу, статуси замовлень, каса, товари, склад, комунальні) — [FINANCE.md](FINANCE.md).
- Тут — рішення директора, ролі, режим відпустки, сповіщення, безпека, інтеграції, AI, інтерфейс.

## 1. Рішення директора (11.11.2026)

| # | Питання | Рішення |
|---|---|---|
| D-1 | Версія релізу канону | **0.3.0** (теги v0.2.0 і v0.2.1 уже існують) |
| D-2 | Минулі замовлення | **Не перераховуються.** Канон діє лише для замовлень, закритих після релізу 0.3.0. Збережені суми старих замовлень незмінні |
| D-3 | P для послуг «від» | P (`price_snapshot`) — **фактична погоджена ціна**, яку вводить майстер або директор під час закриття. 50 % рахується від неї |

| D-7 | Захист PIN бота | 5 невдалих спроб → блокування на 15 хв, **у БД, на користувача** (не лише на чат), переживає перезапуск |

| D-9 | `MDS_ENV` за замовчуванням | `production` (найбезпечніше). Тестові/локальні середовища явно задають `MDS_ENV=test` |
| D-10 | Бот персоналу (Q-12) | Операційні дії **лишаються**: додати, перенести, скасувати запис, «не прийшов», закрити зміну. Прибирається **лише** фінансове закриття замовлення. Закриття замовлень, повернення, сторно — лише у веб-застосунку |

## 3. Ролі (лише дві)

**Майстер** і **Директор**. Директорів двоє (подружжя), права однакові, один одному дії не погоджують.
Ролі «Адміністратор» немає (D-4). Знайдено в коді — це `CANON_MISMATCH`.
Права перевіряються **в сервісі** (`actor.require`), не лише в інтерфейсі.

| Дія | Майстер | Директор |
|---|---|---|
| Створити замовлення (закрити запис) | ✅ свої | ✅ |
| Редагувати замовлення, поки зміна відкрита | ✅ свої (обсяг — Q-3) | ✅ |
| Редагувати замовлення після закриття зміни | ❌ | ✅ |
| Закрити замовлення без матеріалів (позначка) | ✅ | ✅ |
| Позначити «не прийшов» (`no_show`) | ✅ свої | ✅ |
| Примусово закрити зміну (матеріали ввести перед закриттям) | ❌ | ✅ |
| Підтвердити виплату, довільна виплата, бонус за товари | ❌ | ✅ |
| Скасування, повернення, сторно замовлення | ❌ | ✅ |
| Додати товар до замовлення (поки зміна відкрита) | ✅ | ✅ |
| Склад: прихід, інвентаризація | ❌ | ✅ |
| Фінансові звіти, заробіток інших | ❌ | ✅ |
| Свій заробіток | ✅ (поточна зміна + поточний місяць, останні 20 записів) | ✅ |
| Налаштування (ціни, націнки) | ❌ | ✅ |
| Відкрити / закрити свою зміну | ✅ | ✅ |

Майстер **ніколи** не бачить заробітку інших майстрів і частки салону.

## 4. Режим «Ми у відпустці»

- Один режим на обох директорів; вмикає будь-який (`POST /api/settings/vacation-mode`). Автовимкнення через 14 днів.
- Поки режим увімкнено, майстер бачить кнопки «Запитати дозвіл» на 7 дій: скасувати замовлення, повернення,
  сторно/виправлення, примусово закрити зміну, додати матеріали після закриття зміни, інвентаризація, прихід матеріалів.
- Не можна запитати: довільну виплату, бонус за товари, підтвердження виплати за зміну.
- Потік: запит (`permission_requests`) → обидва директори в Telegram → перший, хто підтвердив, виграє → дія
  виконується **один раз** → усе в `audit_log`. Майстер може відкликати запит до рішення.

## 5. Сповіщення

Канали: Telegram і дзвіночок у застосунку. Обидва директори отримують усе, **без дублювання дії**
(хто перший обробив — позначка для обох). Зберігання — черга `notifications` (подія і повідомлення
в одній транзакції; бот доставляє кожні 3 с).

| Рівень | Подія | Кому |
|---|---|---|
| Критичні (не вимикаються) | Салон < 0 у замовленні | обом директорам |
| | Від'ємний баланс майстра (переплата) | обом директорам |
| | Запит дозволу від майстра | обом директорам |
| Важливі (вимикаються) | Зміна заробітку > 50 ₴ | майстру + директорам |
| | Неоплачені замовлення > 3 днів | директорам |
| | Зміна не закрита > 12 год | майстру + директорам |
| Інформаційні (щоденний дайджест) | Рентабельність < 18 % | директорам |
| | Від'ємний залишок на складі | директорам |
| | Неявка; нове замовлення | майстру |
| | Скасування | майстру + директорам |

## 6. Безпека й надійність

- Журнал змін (`audit_log`) — лише зміни, не читання. Журнал входів (`login_events`) — 90 днів, вкладка «Безпека».
- Фінансові дані не видаляються фізично: витрати архівуються; замовлення, `ledger`, `audit_log` — лише додавання.
- Автовихід після 30 хв бездіяльності (Q-5); відкликання сесій з іншого пристрою (`token_version`).
- PIN на вкладці «Фінанси»: раз на сесію, скидає інший директор (Q-6).
- Бекапи: щодня автоматично + вручну; Google Drive через **Service Account** (Q-7); **3 незалежні копії**
  (сервер, зашифрована копія на Google Drive, локальний ПК); зберігати 30 днів; перевірка цілісності;
  описана й перевірена процедура відновлення; збій → Telegram обом директорам.
- Шифрування: на диску (БД) і HTTPS. Секрети — лише змінні середовища. Залежності — зафіксовані версії.
- Хостинг: VPS (Railway — тимчасово).
- Деталі реалізації — [SECURITY.md](SECURITY.md), [OPERATIONS.md](OPERATIONS.md).

## 7. Інтеграції

- **MDs Manager** (`ikenlo/md-manager`, окремий продукт): **pull** — Manager сам читає з Connect через
  `/api/ext/v1` (лише GET), раз на годину, ключ API + HTTPS. Отримує: ціни закупівлі, витрати за послугами/майстрами,
  витрату матеріалів, залишки, візити, витрати на рекламу. Повертає лише **рекомендації** (Q-10). Connect —
  єдине джерело правди для записів, грошей і складу (D-5).
- **SMS, Google Calendar, Instagram, Facebook** — збирає MDs Manager. Connect нічого не надсилає (D-6a).
- **Вебхуки Meta** (з 0.3.1): Connect приймає їх (перевірка `MDS_META_VERIFY_TOKEN`, підпис `MDS_META_APP_SECRET`)
  і кладе в чергу `webhook_queue`; Manager читає чергу й підтверджує обробку (ack) — єдиний запис від Manager (D-5).
  Запис у статусі «processing» довше `MDS_WEBHOOK_PROCESSING_TIMEOUT_MINUTES` повертається в чергу.
- **Telegram-бот** — див. [BOT.md](BOT.md): дозволені дії, а не акаунти; роль визначається користувачем
  у системі; операційні дії із записами і змінами + перегляд і підтвердження; фінансові дії — лише на сайті (D-6b, D-10); вхід — спільний код персоналу + особистий PIN (scrypt), D-7.
- **ПриватБанк «Термінал»** — вручну в 0.3.0, автоматично в 0.4.0 (D-6c).

## 8. AI-аналітика

- Абстракція обов'язкова вже зараз: `AIProvider` → `RulesProvider` (за замовчуванням) і `LocalLlamaProvider`
  (HTTP `http://localhost:8080/v1`, llama.cpp + Qwen 2.5 — вмикається лише конфігурацією).
- `POST /api/analytics/recommend`: ланцюжок llama → rules (ніколи не показувати «помилка AI»), кеш 1 год або ручне оновлення.
- `GET /api/finance/insights` (порівняння з попереднім періодом, тренди) лишається окремо.
- Промпт — `mds/prompts/financial_analysis.md` (англійською, відповідь українською). У промпт — лише агрегати, без персональних даних.

## 9. Інтерфейс

- Мова — українська. Звіти: кожен можна вимкнути (ховається, дані рахуються); експорт PDF + Excel/CSV.
- Вкладки «Фінанси», «Аналітика» (директор) і «Мої фінанси» (майстер) — порядок блоків у [FINANCE.md](FINANCE.md) §5.
- **Календар:** зайняті слоти — темно-червоне напівпрозоре тло з часом (`13:40–15:25`) (Q-9); іконка, назва і
  тривалість послуги (`Фарбування · 2:30`); якщо послуга не вміщується — блокувати і запропонувати найближчі вікна.
  Спершу телефон, зручно пальцем.
- **«Логіка системи»** (директор): схеми Mermaid — поділ замовлення (середні цифри місяця за каноном),
  життєвий цикл замовлення, зміна і каса. Mermaid v11 — локальний файл `static/vendor/`, вантажиться лише на цій
  сторінці; цифри — `GET /api/finance/logic-stats`.
