# Аудит MDS Connect — версія 0.1

Дата: 2026-11-03. Контрольна точка: тег Git `v0.1`. Розгорнуту версію показує
`GET /api/health` → `{"ok": true, "version": "0.1.0"}`.

## 1. Що перевірено

| Область | Як перевірено |
|---|---|
| Структура проєкту | `server/mds`: `api` (роутери) → `services` (уся логіка) → `models` + Alembic; `bot`; `web/static` (PWA) |
| Синтаксис і стиль | `ruff check mds tests`, `node --check app.js / sw.js` |
| API і маршрути | Усі 50 ендпоінтів: авторизація потрібна всюди, крім `POST /api/auth/login` і `GET /api/health` |
| Авторизація | JWT (HS256) + `token_version` (вихід з усіх пристроїв при зміні пароля), scrypt-хеші паролів, блокування після невдалих спроб |
| Права доступу | Новий тест-матриця `test_permissions.py`: майстер проти чужих записів, замовлень, змін, клієнтів, графіка та всіх функцій директора |
| Фінанси | Новий тест `test_invariants.py`: 5000 випадкових поділів × 3 режими матеріалів; 40 замовлень + 10 виправлень + виплати → журнал = замовлення = дашборд = баланси майстрів |
| Робочі дані (лише читання) | Продакшен: 4 замовлення відповідають `amount = майстер + матеріали + салон`, сума в журналі збігається |
| База даних | `foreign_keys=ON`, WAL, `busy_timeout`; тест «міграції = моделі»; міграції 0001→0010 на порожній базі |
| Telegram-бот | Справжній диспетчер aiogram у тестах; екранування даних у HTML-повідомленнях; перевірка власника запису в кнопках клієнта; черга сповіщень надсилає без HTML |
| Граничні значення | Новий тест `test_edge_inputs.py`: від'ємні/нульові/завеликі суми, невідомі категорії й способи оплати, неіснуючі id, неправильні дати → лише 4xx |
| Frontend | Playwright: 38 сторінок (директор і майстер, ПК і iPhone 13) — без помилок консолі, без HTTP-помилок, без горизонтального прокручування, без `undefined`/`NaN` у тексті |
| Збірка | Чисте віртуальне середовище з `requirements.txt` + `python -m mds start` на порожній базі (міграції, директор, 42 послуги, вхід) |
| Залежності | `pip-audit -r requirements.txt` — відомих вразливостей не знайдено |

## 2. Знайдені помилки

| # | Серйозність | Помилка |
|---|---|---|
| 1 | Висока (приватність) | `POST /api/clients`: майстер міг дізнатися ім'я будь-якого клієнта за номером телефону й перезаписати його нотатки без запису в журнал (логіка була в роутері, а не в сервісі) |
| 2 | Середня | Бот, команда «Сьогодні»: ім'я клієнта не екранувалося в HTML — символи `<`/`>` у імені з Telegram ламали відповідь |
| 3 | Середня | Бот: після «Час зайнятий» клієнт міг повторно натиснути або вибрати кілька запропонованих часів — створювалось кілька записів |
| 4 | Середня | Завеликі числа в сумах/цінах (> 2^63) → помилка сервера 500 замість зрозумілої відповіді |
| 5 | Середня | Склад: не створювався матеріал без ціни (422 англійською), порожня назва/одиниця при редагуванні та нескінченні кількості → 500 *(виправлено перед аудитом, PR #6)* |
| 6 | Низька | Чуже замовлення повертало 422 «Недоступно» замість 403 |
| 7 | Низька | Резервні копії: з'єднання SQLite не закривались (`with sqlite3.connect()` не закриває з'єднання) |
| 8 | Низька | Веб-панель не запускалась, якщо браузер забороняє локальне сховище (приватний режим) |
| 9 | Низька | Кількість матеріалу в замовленні: `1e300` → 500 |

## 3. Що виправлено

Усі помилки 1–9 виправлено без зміни бізнес-правил і дизайну:
- №1 — нова сервісна функція `catalog.create_client` (директор/адміністратор, аудит змін нотаток).
- №2 — `html.escape` для всіх даних у відповіді «Сьогодні» та `/link`.
- №3 — `bookings.client_rebook`: лише зі скасованого запису й без дубля активного запису до того ж майстра на ту ж послугу.
- №4 — спільна базова модель вхідних даних відхиляє цілі числа > 10^12 (10 млрд грн у копійках).
- №6 — `Forbidden` (403).
- №7 — `contextlib.closing`.
- №8 — безпечна обгортка `store` для `localStorage`.
- №9 — розбір кількості через `stock.to_milli` (межа і перевірка).

Кожне виправлення покрите тестом. Дані користувачів, записи, замовлення й фінансова історія не змінювались.

## 4. Проблеми, що залишились (потребують рішення або окремої задачі)

| # | Проблема | Чому не виправлено зараз / рекомендація |
|---|---|---|
| 1 | Резервні копії лежать на тому ж диску Railway, що й база. Втрата диска = втрата і бази, і копій | Потрібне зовнішнє сховище (S3/Google Drive/Telegram-канал директора) — нова функція. **Пріоритет №1 перед реальним запуском** |
| 2 | Перед реальною роботою: змінити пароль директора і код «Для майстрів» `0000`, задати майстрам особисті PIN | Організаційне; зараз свідомо лишено для етапу налаштування |
| 3 | Режими матеріалів «майстер»/«пропорційно»: якщо матеріали дорожчі за частку, заробіток майстра стає від'ємним; якщо матеріали дорожчі за суму — від'ємна частка салону | Формула відповідає FINANCE.md; змінювати лише за рішенням директора (обмежити нулем?) |
| 4 | Директор може виплатити більше, ніж борг (баланс майстра стає від'ємним = аванс) | Свідома гнучкість; за потреби — попередження в інтерфейсі |
| 5 | Стан діалогів бота і лічильник невдалих PIN зберігаються в пам'яті — скидаються при перезапуску сервера | Прийнятно для одного салону; за потреби — сховище в БД |
| 6 | Токен входу зберігається в `localStorage`; немає заголовка Content-Security-Policy | Ризик XSS знижено (DOM лише через `h()`, без `innerHTML` з даними). CSP — окрема задача з перевіркою всіх сторінок |
| 7 | Залежності задані діапазонами версій, а не точними | Перевірені версії: fastapi 0.162.0, starlette 1.7.0, pydantic 2.13.5, SQLAlchemy 2.1.6, alembic 1.20.1, aiogram 3.31.0, PyJWT 2.15.0, uvicorn 0.54.0. Рекомендовано файл фіксації версій |
| 8 | Клієнт у боті може створити багато записів (немає ліміту на клієнта) | За потреби — ліміт активних записів на клієнта |
| 9 | Від'ємний залишок на складі дозволено (закриття замовлення не блокується) | Свідоме рішення (див. `services/stock.py`) |
| 10 | Спосіб оплати «Переказ» прибрано з інтерфейсу, але API його приймає (для старих замовлень) | Сумісність з історією; не заважає |
| 11 | Docker-образ локально не збирався (немає Docker-демона в середовищі аудиту) | Образ збирає Railway при кожному оновленні; збірку з `requirements.txt` перевірено окремо |
| 12 | SQLite — один сервер, без масштабування | Для одного салону достатньо; PostgreSQL підтримується через `MDS_DATABASE_URL` |

## 5. Результати тестів і збірки

- `python -m pytest`: **99 тестів, усі пройдені** (було 94; додано матрицю прав, фінансові інваріанти, граничні значення, тести бота).
- `ruff check mds tests`: без зауважень. `node --check`: без помилок.
- Чиста збірка з `requirements.txt` + старт на порожній базі: успішно.
- Браузер (Playwright): 38 сторінок без помилок консолі.
- CI GitHub Actions: зелений на коміті релізу.

## 6. Стан безпеки

- ✅ Усі ендпоінти, крім входу й `/health`, вимагають токен; ролі перевіряються в сервісах.
- ✅ Майстер бачить лише свої записи, замовлення, зміни, виплати і своїх клієнтів.
- ✅ Паролі — scrypt; блокування після невдалих входів; токени відкликаються зміною пароля.
- ✅ Фінансовий журнал лише на додавання; кожне виправлення має причину й автора.
- ✅ Захист від подвійних записів і подвійного закриття/оплати (блокування + унікальні ключі).
- ✅ Заголовки `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Cache-Control: no-store` для API.
- ✅ Залежності без відомих вразливостей.
- ⚠️ Див. розділ 4: зовнішні бекапи, зміна стартових паролів/кодів, CSP.

## 7. Готовність

Версія 0.1 **стабільна і готова до подальшої розробки**: тести зелені, робочі дані узгоджені,
відомі ризики описані вище. З чого продовжити наступного разу:
1. Зовнішня копія бекапів (щоденна відправка файлу бази директору в Telegram або в хмару).
2. Рішення директора щодо від'ємних заробітків у режимах матеріалів (розділ 4, №3).
3. Фіксація версій залежностей.
