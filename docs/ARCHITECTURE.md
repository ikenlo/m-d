# Архітектура MDS Connect

Поточна будова системи для розробника. Бізнес-правила — [CANON.md](CANON.md) і [FINANCE.md](FINANCE.md);
таблиці — [DATABASE.md](DATABASE.md); ендпоінти — [API.md](API.md); бот — [BOT.md](BOT.md);
запуск і бекапи — [OPERATIONS.md](OPERATIONS.md); безпека — [SECURITY.md](SECURITY.md).
Стан — реліз канону 0.3.0.

## 1. Принципи

1. Один салон. Без мультитенантності, тарифів, реєстрації інших салонів.
2. Один сервер і одна БД. Браузер, Android, Windows і Telegram працюють через один бекенд.
3. Уся бізнес-логіка — у `mds/services`. API і бот лише перетворюють запит → виклик сервісу → відповідь.
4. Гроші — `int` копійки, ставки — bp. Фінансові факти не стираються: виправлення = сторно + новий запис + аудит.
5. Простота для майстра: закриття замовлення в кілька натискань.

## 2. Технології

| Шар | Вибір |
|---|---|
| Бекенд | Python 3.11+ (CI — 3.12), FastAPI, uvicorn |
| БД | SQLite (за замовчуванням, WAL) / PostgreSQL через `MDS_DATABASE_URL` |
| ORM, міграції | SQLAlchemy 2, Alembic |
| Авторизація | JWT HS256 + `token_version`; паролі й PIN — scrypt; 2FA кодом у Telegram |
| Telegram | aiogram 3, long polling |
| Веб-панель | ванільний JS, PWA, без збірки (`app.js` — один файл, DOM лише через `h()`) |
| Застосунки | `apps/android` (WebView, Java), `apps/windows` (Electron) — лише оболонки |
| Тести | pytest; бот — справжній диспетчер aiogram; UI — Playwright smoke (`ui-tests/`) |

## 3. Схема

```
 Браузер / PWA   Android (WebView)   Windows (Electron)       Telegram (клієнти, персонал)
        └──────────── HTTPS, REST /api, JWT ───────────┘                 │ Bot API
                         ┌──────────────┐                        ┌──────────────┐
                         │  mds.api     │                        │  mds.bot     │
                         └──────┬───────┘                        └──────┬───────┘
                                └──────────────┬─────────────────────────┘
   MDs Manager ── /api/ext/v1 (ключ, GET) ──►  ┌▼─────────────┐
                                               │ mds.services │  ← уся логіка і перевірка прав
                                               └──────┬───────┘
                                               ┌──────▼───────┐
                                               │ БД + backups │ → Google Drive
                                               └──────────────┘
```

Усе працює **в одному процесі** (`python -m mds start`): API, бот, фонові цикли. Тому — лише одна репліка.

## 4. Структура коду (`server/`)

```

  models.py        усі таблиці + константи статусів і ролей

  clock.py         локальний час салону (naive, Europe/Kyiv); у тестах підміняється
  security.py      scrypt, JWT
  errors.py        ValidationError 422, Conflict 409, Forbidden 403, NotFound 404, AuthError 401
  perf.py          статистика швидкодії в пам'яті
  wipe.py, demo_fop1.py   очищення і демо-дані (лише тестове середовище, D-8)
```

Сервісна функція: `(session, actor, ...)`, без `commit`; права — `actor.require(...)` / `_check_access`;
помилки — `mds.errors.*`. Telegram — лише через `notifications.enqueue` / `notify_directors`.

## 6. Ключові потоки

1. **Запис:** бот / панель → `bookings.create_appointment` → `_lock_master` (UPDATE `users.booking_lock`) →
   `_check_slot` (перетини, робочі місця, графік) → запис → аудит → сповіщення. Клієнтські канали — з `Actor`
   роллю `client` (антиспам).
2. **Закриття замовлення:** `POST /api/appointments/{id}/close` → `orders.close_order`: перевірка ключа ідемпотентності
   → атомарний `UPDATE appointments … WHERE status IN CLOSABLE` → `compute_split` → автоматичне відкриття зміни →
   замовлення + матеріали → списання складу → `ledger` → `audit`.
3. **Закриття зміни:** перевірка незаповнених замовлень → звіт-знімок → каса ([FINANCE.md](FINANCE.md) §9) → виплата
   «з каси» → статус `closed`/`paid` → сповіщення директорам.
4. **Виплата:** атомарна зміна статусу зміни + `UNIQUE(payouts.shift_id)` → `ledger` → `audit` → сповіщення майстру.
5. **Виправлення:** сторно + нові суми + повернення/списання складу + аудит + сповіщення майстру.
6. **Бекап:** SQLite backup API → `PRAGMA integrity_check` → ротація → Google Drive.

## 7. Додаткові модулі (поза фінансовим каноном)

- **Клієнтська база.** Клієнт — одна сутність `clients` для записів, замовлень і повідомлень. Пошук номера і серед
  основних, і серед додаткових телефонів; об'єднання дублікатів (директор) переносить записи й замовлення.
  Статистика (візити, середній чек, інтервал) рахується з `orders` і `appointments`, нічого не дублюється.
  Сегменти (`client_seg_*`): неактивний ≥ 90 дн., давно не був ≥ 45 дн., VIP ≥ 10 візитів або ≥ 10 000 ₴,
  постійний ≥ 3 візити, новий. Знеособлення за запитом клієнта стирає персональні дані, суми лишаються.
- **Податки і зарплата.** Ставки — лише записи `tax_rates` з датами (у коді ставок немає); нова ставка закриває
  попередню. Офіційна зарплата ≠ управлінський поділ 50 %. Нарахування — брутто, ПДФО і ВЗ утримуються,
  ЄСВ зверху; виправлення — сторно + нове (знімок ставок). Кадрові дані — `employee_profiles`.
  Квартальна відомість і CSV для бухгалтера; нагадування про строки податків ФОП за 5 днів.
- **«Термінал» ПриватБанку (NFC).** Наразі код уміє: створити оплату (`card_payments`), відкрити застосунок банку
  deeplink-ом, перевірити результат у банку (`check.php`, лише `response_code = "00"`) і закрити замовлення з ключем
  `card-<id>`. Режими `card_terminal_mode`: `off` / `mock` (лише `MDS_ENV=test`); `live` заборонено до 0.4.0 (`AUTO_CLOSE_ENABLED`, D-6c):
  майстер обирає «Картка» після оплати; автоматичне закриття повертається в 0.4.0.
- **POS-термінал ПриватБанку (PAX/Newland, ECR по TCP).** Режим `ecr` у тій самій `card_payments`: сервер сам
  з'єднується з терміналом у локальній мережі салону (з Railway недоступно — потрібен локальний сервер або VPN),
  обмін іде поза транзакцією БД, замовлення закривається після «схвалено» з RRN. Вимкнено — ручне підтвердження
  `confirm()`. Детально — [TERMINAL.md](TERMINAL.md).
- **Швидкодія.** gzip; статика з `?v=<версія-хеш>` і довгим кешем; власні шрифти; скелети; таймаути API 20/30 с;
  дедуплікація GET; `joinedload`/`selectinload` проти N+1; індекси (міграція 0023); `Server-Timing`,
  `/api/perf` і RUM із браузера (лише назви сторінок і мс). Свідомо **не** використовуємо: SSR, фреймворки,
  Redis, балансування, OpenTelemetry.

## 8. Відомі слабкі місця

- Один процес: падіння зупиняє і API, і бота, і фонові цикли.
- `app.js` — понад 4 000 рядків в одному файлі; нові вкладки канону його ще збільшать.
- `ledger` — лише додавання за домовленістю (немає захисту на рівні БД); рядки `shift_closed` — підсумкові,
  читачі фільтрують за `kind`.
- Одночасні правки двох директорів ловить `version` (SQLAlchemy `version_id_col`) → 409; клієнт має оновити дані.
