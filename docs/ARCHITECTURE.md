# Архітектура MDS Connect

## 1. Принципи

1. **Один салон.** Без мультитенантності, тарифів, реєстрації інших салонів.
2. **Єдина база даних і єдиний сервер.** Усі клієнти (Android, Windows, Telegram) працюють через
   один бекенд — дані завжди узгоджені.
3. **Уся бізнес-логіка — в одному місці** (`mds/services`). API, бот і майбутні застосунки лише
   викликають сервіси. Правило змінюється в одному файлі — і діє всюди.
4. **Гроші — цілі копійки**, відсотки — базисні пункти (5000 = 50%). Жодних float у фінансах.
5. **Фінансові факти не стираються.** Виправлення = сторно + нове проведення + запис в історії.
6. **Простота для майстра.** Закриття замовлення: «Закрити» → сума (підставлена) → спосіб оплати → «Закрити замовлення».

## 2. Технології

| Шар | Вибір | Чому |
|---|---|---|
| Бекенд | Python 3.11+, FastAPI | Простий, швидкий, автоматична документація API (`/docs`) |
| БД | SQLite (за замовч.) / PostgreSQL | Для одного салону SQLite достатньо; перехід на PostgreSQL — зміною `MDS_DATABASE_URL` |
| ORM / міграції | SQLAlchemy 2 + Alembic | Схему можна змінювати без втрати даних |
| Авторизація | JWT (HS256) + scrypt-хеші паролів | Стандартна бібліотека, без зовнішніх сервісів |
| Telegram | aiogram 3 (long polling) | Не потребує публічного URL / HTTPS для бота |
| Веб-панель | Ванільний JS, PWA | Без збірки, встановлюється на Android/Windows як застосунок |
| Нативні застосунки (етап 2) | Flutter (Android + Windows з одного коду) | Одна кодова база для обох платформ, той самий REST API |

## 3. Схема

```
 ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌────────────────┐
 │ Android      │  │ Windows      │  │ Браузер      │  │ Telegram       │
 │ (PWA→Flutter)│  │ (PWA→Flutter)│  │ (панель)     │  │ клієнти/персонал│
 └──────┬───────┘  └──────┬───────┘  └──────┬───────┘  └───────┬────────┘
        │   HTTPS / JSON (REST API, JWT)    │                  │ Bot API
        └──────────────┬───────────────────-┘                  │
               ┌───────▼────────┐                     ┌────────▼────────┐
               │  mds.api       │                     │  mds.bot        │
               │  (FastAPI)     │                     │  (aiogram)      │
               └───────┬────────┘                     └────────┬────────┘
                       └───────────────┬───────────────────────┘
                               ┌───────▼────────┐
                               │ mds.services   │  ← уся бізнес-логіка
                               └───────┬────────┘
                               ┌───────▼────────┐
                               │ БД (SQLite/PG) │ + data/backups/
                               └────────────────┘
```

Сповіщення Telegram йдуть через таблицю-чергу `notifications` (outbox): подія і повідомлення
записуються в одній транзакції, бот доставляє чергу кожні 3 секунди. Повідомлення не губляться,
навіть якщо Telegram тимчасово недоступний.

## 4. Структура коду

```
server/
  mds/
    config.py        конфігурація (змінні MDS_*)
    db.py            підключення до БД, транзакції
    models.py        таблиці + константи статусів/ролей
    money.py         копійки, відсотки, форматування
    clock.py         «поточний час» (підміняється в тестах)
    security.py      паролі (scrypt), JWT
    errors.py        доменні помилки → HTTP-коди
    services/
      common.py        Actor (хто діє), журнали audit/ledger, налаштування
      users.py         акаунти, вхід, блокування, умови оплати майстра
      catalog.py       послуги, матеріали, клієнти
      bookings.py      календар, вільні слоти, захист від подвійних записів
      finance.py       формула поділу виручки (чиста функція)
      orders.py        закриття замовлень, зміни, звіти, виплати, виправлення
      expenses.py      витрати салону
      analytics.py     фінансова панель і розрізи
      notifications.py черга Telegram-сповіщень
      backup.py        резервні копії
      journal.py       читання журналів
    api/             FastAPI: deps (авторизація), schemas, routers/*
    bot/             Telegram: views (тексти/кнопки), handlers (клієнти), staff (розділ персоналу), runner
    web/static/      веб-панель (index.html, app.js, style.css, PWA)
  migrations/        Alembic
  tests/             pytest: сервіси, API, бот (зі справжнім диспетчером), паралельність
```

## 5. Модель даних

| Таблиця | Призначення |
|---|---|
| `users` | Співробітники: роль, пароль, індивідуальний `share_bp` і `materials_mode`, графік, Telegram |
| `services`, `master_services` | Послуги (ціна, тривалість) і які послуги виконує майстер |
| `materials` | Довідник матеріалів (собівартість за одиницю) |
| `clients` | Клієнти (телефон унікальний, прив'язка Telegram) |
| `appointments` | Записи: майстер, послуга, час, статус, джерело |
| `orders`, `order_materials` | Закриті замовлення: сума, матеріали, оплата, **знімок умов** і розрахунок часток |
| `shifts` | Зміни майстрів і знімок звіту на момент закриття |
| `payouts` | Фактичні виплати майстрам (унікальна на зміну) |
| `expenses` | Витрати салону (м'яке видалення) |
| `ledger` | Журнал фінансових операцій — лише додавання |
| `audit_log` | Історія змін усіх сутностей: хто, коли, було/стало, причина |
| `settings` | Налаштування салону (стандартний відсоток, графік, крок слотів…) |
| `notifications` | Черга Telegram-повідомлень |

Статуси запису: `pending → confirmed → in_progress → completed`, а також `cancelled`, `no_show`.
Статуси зміни: `open → closed (очікує виплати) → paid`.

## 6. Надійність і безпека

| Вимога | Реалізація |
|---|---|
| Захищена авторизація | Бот: спільний код персоналу + особистий PIN (scrypt), блокування після 5 спроб. Панель: scrypt-хеші, JWT з терміном дії, блокування після 5 невдалих спроб на 15 хв, вимоги до пароля |
| Відкликання сесій | `token_version`: зміна/скидання пароля чи деактивація завершує всі сесії |
| Розмежування прав | Перевірки в сервісах (`Actor.require`), а не лише в UI. Майстер бачить тільки свої записи і гроші |
| Подвійні записи | Блокування рядка майстра (`booking_lock`) у транзакції + перевірка перетинів; протестовано паралельними потоками |
| Повторне проведення оплати | Атомарний перехід статусу запису, `UNIQUE(orders.appointment_id)`, ключ ідемпотентності, `UNIQUE(payouts.shift_id)` |
| Журнал фінансових операцій | `ledger` (append-only) |
| Історія редагувань | `audit_log` для записів, замовлень, витрат, користувачів, налаштувань |
| Виправлення директором | `PATCH /api/orders/{id}` з обов'язковою причиною → сторно + нове проведення + аудит + сповіщення майстру |
| Резервні копії | Щоденно (SQLite backup API + перевірка цілісності), ротація N копій, кнопка «Створити копію» |
| Захист від XSS | Панель будує DOM без `innerHTML` для даних; бот екранує HTML |

## 7. Як розширювати

Новий функціонал додається як:
1. Функція в `services/*` (+ тест у `tests/`).
2. Ендпоінт у `api/routers/*` (+ тест API).
3. Екран у `web/static/app.js` (`VIEWS.назва` + пункт у `NAV`) і/або обробник у `bot/handlers.py`.
4. Якщо змінено `models.py` — міграція Alembic (тест `test_migrations_match_models` нагадає).
