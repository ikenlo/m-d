# План: спрощений бухгалтерський облік M&D

Статус: **на погодження**. Версія системи на момент аналізу — 0.1.15.
Принцип: M&D лишається системою управління салоном. Майстер працює лише із записами й замовленнями;
облік збирається автоматично; звітність складає й подає бухгалтер. Нічого не подаємо в ДПС самі.

Головні правила обліку:
- **Дохід ФОП** = усе, що заплатили клієнти (каса + банк), на дату оплати. Частка майстра, комісія банку та
  витрати дохід ФОП **не зменшують**.
- **Управлінська виручка і прибуток** — окремо: виручка − частки майстрів − матеріали − витрати.
- Поділ 50/50 — управлінський розрахунок, **не** офіційна зарплата. Офіційна зарплата — лише для найманих
  (блок «Податки і зарплата»).
- Банківська виписка ≠ фіскалізація: виписка підтверджує гроші, Checkbox — чек.

## 2. Чого бракує (мінімальні зміни)

### Етап 1 — без зовнішніх інтеграцій (можна одразу)
1. **Excel «Сформувати звіт для бухгалтера» — 7 аркушів за ТЗ** (переробка наявного):
   Доходи ФОП · Готівкові надходження · Банківські надходження · Фіскальні чеки та повернення ·
   Витрати салону · Нарахування та виплати майстрам · Підсумок. Довільний період (з — по), а не лише рік/квартал.
2. **Повернення і статус оплати в реєстрі доходів.** Зараз повернення = виправлення суми замовлення.
   Додати в реєстр колонки «повернено» і «статус» (оплачено / повернення / виправлено) з журналу виправлень —
   без нових таблиць.
3. **Витрати:** поле «спосіб оплати» (готівка/картка/рахунок), категорії «Обладнання» і «Господарські витрати»,
   **фото або файл чека** (зберігання на диску Railway поруч із базою, до 10 МБ, jpg/png/pdf; потрапляють у резервні копії).
   Міграція: `expenses.payment_method`, таблиця `expense_files`.
4. **Звіт по кожному майстру** за період: нараховано, виплачено (з датами), списання, залишок — на екрані й в Excel.
   Дані вже є, потрібні лише звіт і експорт.
5. **Екран керівника** (доповнення «Огляду»): виручка сьогодні, готівка, картка, дохід ФОП за період, витрати,
   нараховано майстрам, фактично виплачено, управлінський прибуток; плитки «чеків», «без фіскалізації»,
   «незвірені банківські операції» з'являться після етапів 2–3.
6. **Календар податків і звітності** на одній вкладці: строки ЄП/ВЗ (до 20 числа), ЄСВ (квартал), декларація,
   звіти по найманих — з наявних ставок і нарахувань; позначки «сплачено/прострочено».

### Етап 2 — Checkbox (ПРРО)
- Перенести модуль з PR #16 на поточну версію (без податків — вони вже злиті), міграція одна.
- Чек створюється в транзакції закриття замовлення → фіскальний номер, статус, посилання ДПС у замовленні;
  повернення → чек повернення; зміни, X/Z-звіти; помилки й «замовлення без чека» — на екрані керівника і в Excel.
- Для ФОП 1 групи ПРРО **необов'язковий** — модуль вмикається в налаштуваннях (за замовчуванням вимкнено).
- Потрібно від вас: акаунт Checkbox, тестова каса (ключ ліцензії, PIN касира) → змінні Railway.

### Етап 3 — monobank
- **Виписка:** API monobank (`/personal/statement`, токен з api.monobank.ua, рахунок ФОП видно в клієнтській
  інформації). Обмеження: 1 запит на 60 с, до 31 доби за запит → фонове завантаження раз на годину/добу.
  Альтернатива без токена — **імпорт файлу виписки** (CSV/XLSX з застосунку).
  Таблиця `bank_transactions` (унікальний id операції), автоматичне зіставлення з картковими замовленнями
  (сума + час ± вікно, як у вже написаній звірці ПриватБанку), список «незнайдених», підсумок надходжень.
- **Термінал у смартфоні monobank** (якщо оберете замість ПриватБанку): інтеграція deeplink для Android
  (сума в копійках, повернення результату) — за аналогією з уже зробленою інтеграцією «Термінала» ПриватБанку.
- Потрібно від вас: токен monobank (лише в змінній Railway), відповідь банку щодо інтеграції термінала.

### Етап 4 — файли для ДПС
- Уже є: XML річної декларації 1 групи (F0103407 + Додаток 1) за офіційними схемами ДПС.
- Звіти по найманих (Податковий розрахунок) — лише дані (CSV/Excel) для бухгалтера; XML — після підтвердження
  форми з бухгалтером. Самостійного подання в ДПС не робимо.

## 3. Структура бази: зміни

| Етап | Зміна | Навіщо |
|---|---|---|
| 1 | `expenses.payment_method` (cash/card/account) | спосіб оплати витрати |
| 1 | `expense_files` (expense_id, назва, тип, розмір, шлях, хто/коли) | фото/документ витрати |
| 2 | `fiscal_receipts`, `fiscal_shifts`, `fiscal_reports`, `fiscal_operations` (з PR #16) | чеки, зміни, Z-звіти |
| 3 | `bank_transactions` (джерело, id, час, сума, опис, контрагент, order_id, статус зіставлення) | виписка й звірка |

Інші вимоги покриваються наявними таблицями (`orders`, `ledger`, `audit_log`, `shifts`, `payouts`, `tax_*`,
`payroll_*`). Інваріанти (копійки, журнал лише на додавання, сторно) зберігаються.

## 4. Інтеграції: що реально доступно

| Сервіс | API | Статус у M&D | Що потрібно |
|---|---|---|---|

| monobank — виписка | ✅ особистий API (токен), 1 запит/60 с | немає | токен |

| СОТА API | лише документообіг з контрагентами | не потрібно | — |

## 5. Порядок і оцінка

1. **Етап 1** — 1 PR на кожен пункт або 2 PR (Excel+реєстр; витрати+майстри+екран+календар). Без нових
   залежностей від банків. Тести на конкретних сумах, перевірка в браузері.
2. **Етап 2** — після тестових ключів Checkbox (або одразу в режимі імітації).
3. **Етап 3** — після вибору банку (monobank) і токена.
4. **Етап 4** — за потреби бухгалтера.

Кожна зміна — окрема гілка + PR, CI зелений, нова версія 0.1.N. Поточна система не ламається: нові модулі
вимкнені за замовчуванням, наявні дані не змінюються.

## 6. Питання для погодження

1. Банк для терміналу й виписки — **monobank** (рекомендація бухгалтера) чи ПриватБанк (інтеграція вже є)?
2. Checkbox підключаємо зараз (ФОП 1 групи — необов'язково) чи пізніше?
3. Фото чеків витрат — зберігати на сервері (Railway, у резервних копіях) чи в Google Drive?
4. Excel за довільний період (з — по) замість рік/квартал — підходить бухгалтеру?
