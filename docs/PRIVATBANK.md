# ПриватБанк «Автоклієнт» — інтеграція (лише читання)

Статус: **реалізовано й протестовано на імітації** (емулятор HTTP + `FakeBankProvider`). Реальних запитів до банку
не було. За замовчуванням вимкнено (`privat_mode = off`). Реальне підключення заблоковано, доки на сервері не задано
`MDS_BANK_LIVE_ALLOWED=yes`. Гілка `feature/privatbank-readonly` чекає відповідей банку на питання з розділу 4.

Джерело: офіційний документ «Опис API для взаємодії з серверною частиною Автоклієнта, версія 3.0.0» (Google Docs від банку).
Номери рядків нижче (р. N) — у текстовій копії цього документа.

## 1. Навіщо

Звірка **оплат карткою** в салоні з банком. Ланцюжок:

1. Майстер закрив замовлення з оплатою «картка» (MDS).
2. Клієнт оплатив на POS-терміналі ПриватБанку (еквайрингова виписка).
3. Банк зарахував гроші на рахунок ФОП за мінусом комісії (виписка за рахунком).

Також для довідки: залишок на рахунку та виписка за період. Платежі, підписи й зарплатні відомості **не реалізовано
і заборонено в коді**.

## 2. Що взято зі специфікації (перевірено вручну)

| Що | Специфікація | Як у нас |
|---|---|---|
| Доступ | для ФОП — у будь-якому тарифі (р. 58) | — |
| Заголовки | `User-Agent`, `token`, `Content-Type: application/json;charset=cp1251` (рр. 71–74); підтримуються utf8 і cp1251 (р. 75) | `User-Agent: MDS-Connect/<версія>`, `token`, `Content-Type: application/json;charset=utf8`; відповідь розбираємо за її charset (utf-8 або cp1251) |
| TLS | 1.0/1.1 не підтримуються (р. 57) | системний TLS (1.2/1.3) |
| Частота | не частіше 1 запиту/с (р. 59) | пауза ≥ 1 с між запитами |
| Обмеження токена | «Обмеження по сервісам» (рр. 67–69) | рекомендуємо залишити лише читання (див. §5) |
| Серверні дати | `GET /api/statements/settings`; `phase ≠ WRK` → можливі помилки (р. 103), `work_balance = Y` → не робити запитів (р. 98) | перевіряємо перед звіркою; інакше «регламентні роботи, спробуйте пізніше» |
| Баланс | `GET /api/statements/balance?acc&startDate&endDate` (ДД-ММ-РРРР) | так |
| Виписка | `GET /api/statements/transactions`, пагінація `exist_next_page` → `next_page_id` → `followId` (р. 123), `limit` ≤ 500, рекомендовано ≤ 100 | `limit=100`, проходимо всі сторінки |
| Унікальність транзакції | `REF + REFN` (р. 124) | ключ `REF/REFN`, дублікати між сторінками відкидаються |
| Напрям | `TRANTYPE` D/C (р. 191), суми без знака | C → надходження, D → списання |
| Стан | `PR_PR`: p проводиться, t сторнована, r проведена, n забракована (р. 178) | у підсумках рахуємо лише `r` |
| Еквайринг | `POST /api/equiring/statements` {account, dateFrom, dateTo (yyyy-MM-dd), page, numberRecords, statementsDateType}; різниця дат ≤ 1 дня (р. 2648) | окремий запит на кожен день: `dateFrom = dateTo = день`, `TRANSACTION_DATE`, `numberRecords=100`, `page` 1, 2… поки `existNextPage` |
| Помилки | 401 токен, 400 формат, 403 вимкнено в налаштуваннях, 500/502, 503/504 (рр. 431–436) | 401/403 → «Банк відхилив доступ», 4xx → «відхилив запит», 5xx/тайм-аут → «тимчасово недоступний» |

Поля еквайрингу **не мають опису** в специфікації. Ми трактуємо їх за прикладом (рр. 2665–2710), де
`Tran_Amt 10.0 = Acq_Amt 0.13 + Ret_Amt 9.87`:

| Поле | Наше трактування (потребує підтвердження) |
|---|---|
| `Tran_Amt` | сума операції; від'ємна — повернення/сторно |
| `Acq_Amt` | комісія еквайра |
| `Ret_Amt` | сума до зарахування на рахунок |
| `Tran_Fee` | додаткова комісія (додаємо до комісії) |
| `Summ` | дублює `Tran_Amt` (не використовуємо в розрахунку) |
| `Date` | дата і час операції на терміналі (вважаємо київським часом) |
| `TranRetPos` | дата зарахування на рахунок |
| `Extr_Rrn`, `Tran_Approval`, `Ident_Ter`, `Pan` | RRN, код авторизації, термінал, маска картки |

## 3. Як налаштована логіка звірки (за день)

1. **Продажі.** Беремо замовлення MDS за день з оплатою «картка» і операції еквайрингу за той самий день.
   Кожну операцію з додатною сумою зіставляємо з одним замовленням: **сума збігається до копійки** і час операції в межах
   ±2 год від закриття замовлення; з кількох однакових сум беремо найближче за часом. Якщо в `Date` час `00:00:00`,
   час не порівнюємо.
2. **Розбіжності.** Звіт показує замовлення без операції в терміналі, операції без замовлення, а також повернення
   (від'ємні суми). Повернення показуємо для ручної перевірки — автоматично не зіставляємо.
3. **Підсумки.** Сума замовлень карткою; продажі, повернення, комісія (`Acq_Amt + Tran_Fee`), до зарахування (`Ret_Amt`).
   Різниця = продажі − повернення − замовлення карткою.
4. **Зарахування.** Суми `Ret_Amt` групуємо за датою `TranRetPos`. На кожну дату шукаємо у виписці рахунку **одне**
   проведене надходження (C, `PR_PR = r`) на точно таку саму суму. Не знайшли — «зарахування не знайдено одним платежем»
   і список надходжень того дня для ручної перевірки.
5. Звірка **нічого не записує** в базу: ledger, замовлення й журнал не змінюються. Права — лише директор.

## 4. Питання до підтримки ПриватБанку (готовий текст)

> Добрий день! Ми ФОП, підключаємо API «Автоклієнт» (документ «Опис API… версія 3.0.0») **лише для читання**:
> виписка за рахунком і еквайрингова виписка за терміналами, щоб звіряти оплати карткою з нашим обліком.
> Платежів через API не створюємо. Просимо підтвердити, чи правильно ми зрозуміли логіку.
>
> **Доступ і токен**
> 1. Які сервіси позначити в «Обмеження по сервісам», щоб працювали лише «Отримання балансів і транзакцій» та
>    «Отримання виписки за терміналами (еквайрингова виписка)», а платежі були вимкнені? Чи є еквайринг окремим пунктом?
> 2. Чи має токен строк дії? Як його відкликати або замінити, якщо є підозра, що він потрапив до сторонніх?
> 3. Обмеження за IP: поле необов'язкове? Наш сервер у хмарі без постійної IP-адреси — чи можна працювати без нього?
> 4. Яке значення `User-Agent` очікуєте? Ми надсилаємо `MDS-Connect/<версія>`.
> 5. Ми надсилаємо `Content-Type: application/json;charset=utf8`. Відповідь тоді теж буде в UTF-8? Чи підходить це
>    і для `POST /api/equiring/statements`, де в документі вказано просто `application/json`?
> 6. Що повертається при перевищенні частоти (більше 1 запиту/с) — 429 чи інший код?
>
> **Виписка за рахунком (`/api/statements/transactions`)**
> 7. Чи правильно, що `TRANTYPE = C` — надходження на наш рахунок, а `D` — списання, і `SUM` завжди без знака?
> 8. `REF + REFN` — постійний ключ? Чи не змінюється він, коли операція переходить з проміжної (interim) у підсумкову
>    (final) виписку? Чи можна покладатися на `ID` / `TECHNICAL_TRANSACTION_ID`?
> 9. Сторно (`PR_PR = t`): змінюється стан наявного рядка чи з'являється окремий рядок із протилежним напрямом?
> 10. `endDate` включно? За який максимальний період можна запитати транзакції одним запитом (з пагінацією)?
> 11. Що означає `FL_REAL = i`?
> 12. Чи правильні шляхи `/api/statements/transactions/interim` і `/api/statements/transactions/final`
>     (у документі «balance(або transactions)/interim»)?
>
> **Еквайрингова виписка (`/api/equiring/statements`)**
> 13. Поля відповіді не описані. Чи правильно ми розуміємо: `Tran_Amt` — сума операції, `Acq_Amt` — комісія банку,
>     `Ret_Amt` — сума до зарахування (`Tran_Amt = Acq_Amt + Ret_Amt`), `Tran_Fee` — додаткова комісія, `Summ` — те саме,
>     що `Tran_Amt`, `TranRetPos` — дата зарахування на рахунок, `TranPost` — дата обробки, `Date` — дата і час операції
>     на терміналі (за київським часом?), `Extr_Rrn` — RRN, `Tran_Approval` — код авторизації, `Ident_Ter` — ID терміналу?
> 14. Повернення на терміналі: від'ємна `Tran_Amt` з тією самою RRN, що й покупка? Чи є окрема ознака повернення
>     або скасування?
> 15. «Різниця між датами не більше 1 дня»: ми запитуємо `dateFrom = dateTo = день`. Чи повертає це всі операції за цей
>     день (дата включно)? Приклад у таблиці (2024-01-01 … 2024-01-31) суперечить обмеженню — що правильно?
> 16. Пагінація: збільшуємо `page` (1, 2, …), поки `existNextPage = true`. Чи правильно? Для чого `nextPageId`?
>     Яке максимальне `numberRecords`?
> 17. Чи є унікальний ідентифікатор операції еквайрингу? Зараз ми складаємо ключ із `Extr_Rrn + Tran_Approval + Date +
>     Tran_Amt + Ident_Ter`.
> 18. Через скільки часу операція з'являється в еквайринговій виписці після оплати? Чи можуть дані за день змінюватися
>     заднім числом?
> 19. Поле `account` — це IBAN рахунку ФОП, на який зараховується еквайринг (UA…)?
>
> **Зарахування еквайрингу на рахунок**
> 20. Як зарахування за терміналом виглядає у виписці рахунку: один платіж за день на суму всіх `Ret_Amt` за `TranRetPos`,
>     чи окремо за кожну операцію? Як розпізнати такий платіж (`OSND`, контрагент, `AUT_CNTR_ACC`)?
> 21. Комісія завжди утримується з суми зарахування (нетто), чи може списуватися окремим платежем (наприклад, раз на місяць)?
> 22. У вихідні та святкові дні (`dates_without_oper_day`) зарахування переноситься на наступний операційний день?

## 5. Як підключити (коли банк відповість)

1. «Приват24 для бізнесу» → «Інтеграція (Автоклієнт)» → «Підключити API», назва `MDS Connect`, IP — не вказувати
   (або після відповіді на питання 3).
2. Налаштування застосунку → «Обмеження по сервісам» → позначити **лише** баланси/транзакції та еквайрингову виписку
   (відповідь на питання 1). Платежі — не позначати.
3. Токен — **лише** у змінній Railway `MDS_PRIVAT_TOKEN`. Не надсилати в чат, пошту чи месенджер і не зберігати в коді.
4. Окреме погодження директора → змінна `MDS_BANK_LIVE_ALLOWED=yes`.
5. Налаштування: `privat_account` = IBAN, `privat_mode` = `live`. Потім `POST /api/bank/check` і звірка за вчорашній день.

## 6. API (лише директор)

| Запит | Що робить |
|---|---|
| `GET /api/bank/status` | режим, рахунок, чи дозволено live, чи задано токен (так/ні) |
| `POST /api/bank/check` | серверні дати банку (phase/work_balance) — перевірка з'єднання |
| `GET /api/bank/balance?on=` | баланс на дату |
| `GET /api/bank/statement?start=&end=` | виписка (≤ 31 дня): надходження, списання, не проведені |
| `GET /api/bank/acquiring?start=&end=` | еквайринг (≤ 7 днів, запит на кожен день) |
| `GET /api/bank/reconcile?day=` | звірка за день (§3) |

Налаштування `privat_mode` (off/mock/live) і `privat_account` (IBAN) — через `PUT /api/settings`.

## 7. Тести (`tests/test_bank.py`, 20)

- Білий список: платежі, підписи, відомості, SWIFT, квитанції — відмова **до** мережевого запиту.
- Заголовки, формат дат ДД-ММ-РРРР, пагінація `followId`, `limit=100`, пауза 1 с між запитами.
- Суми рядками («100.50», «1 234,56») і числами (−10.0) → копійки; дублікати REF/REFN відкидаються.
- Приклад еквайрингу зі специфікації: 1000 = 13 + 987, повернення −1000; тіло запиту і `page` 1 → 2; відповідь у cp1251.
- Помилки 401/403/400/500/503/тайм-аут → зрозумілі повідомлення; токена немає ні в помилках, ні в `repr`.
- `phase ≠ WRK` → «регламентні роботи».
- Live заблоковано без дозволу сервера; без токена клієнт не створюється; статус не повертає токен; перевірка IBAN.
- Звірка на конкретних сумах: 3 замовлення карткою (1600 ₴) і 3 операції (1400 ₴, комісія 18,20 ₴, до зарахування
  1381,80 ₴); знайдено замовлення без оплати й оплату без замовлення; зарахування 1381,80 ₴ на 21.10 знайдено.
  Однакові суми зіставляються за часом; повернення позначається; звірка не пише в БД.
- Права: адміністратор і майстер — 403 на всі `/api/bank/*`.

## 8. Чого немає (свідомо)

- Інтерфейсу в панелі — додамо після відповідей банку, щоб не переробляти.
- Збереження виписок у БД, автоматичних проведень у ledger, створення платежів, квитанцій PDF.
- Режиму групи ПП (для одного ФОП не потрібен; без `ID` запити працюють).
