## 1. Загальна оцінка

**Система зріла, добре документована і суворо відповідає канону.**

Сильні сторони:
- Чіткий поділ: `services/` = уся бізнес-логіка, API/бот = тонкі адаптери.
- Гроші тільки в копійках, формула поділу в одному місці (`compute_split`).
- Аудит, ідемпотентність, оптимістичне блокування (`version`), захист від подвійних дій на рівні БД.
- Канон як єдине джерело правди + відкриті питання (Q-*) явно зафіксовані.
- Добра тестова культура та CI.

Головні ризики / зони покращення:
- Монолітні файли (`models.py` ~40k, `app.js` >4000 рядків).
- Один процес (падіння = все лягає).
- Застарілі поля та таблиці (заплановано в 0.3.3, але ще живуть).
- Відсутність повної матриці прав (роль × ендпоінт).
- Підготовка до масштабування (хоча це свідомо один салон).

## 2. Архітектурні спостереження

### 2.1. Моноліти

| Файл | Проблема | Пропозиція |
|------|---------|------------|
| `server/mds/models.py` (~40 кБ) | Усі моделі + константи статусів в одному файлі | Розбити на пакети: `models/base.py`, `models/catalog.py`, `models/finance.py`, `models/calendar.py`, `models/enums.py`. Реекспорти з `models/__init__.py`. |
| `mds/web/static/app.js` (>4 000 рядків) | Важко навігувати, неможливо нормально рев'ювити | Розбити на модулі за вкладками (`views/calendar.js`, `views/finance.js` тощо) + завантажувати через простий збірник або нативні ES modules (якщо браузер дозволяє). Зберегти `h()`. |
| Окремі сервіси (`orders.py`, `bookings.py`, `analytics.py`) | Великі файли | Виділити підмодулі (напр. `orders/close.py`, `orders/correct.py`, `orders/shift.py`). |

### 2.2. Один процес

З `ARCHITECTURE.md` §3: API + бот + фонові цикли в одному процесі → лише одна репліка.

**Пропозиції:**
- Короткостроково: додати health-check і автоперезапуск (вже є в плані 1.0.0).
- Середньостроково: винести Telegram-polling і нагадування в окремий worker-процес (або хоча б окремий потік), щоб падіння API не зупиняло бота.
- Довгостроково: розглянути винесення фонових завдань (бекап, нагадування, дайджест) у чергу (RQ/Celery/або простий APScheduler в окремому контейнері).

### 2.3. Застарілі сутності

З `ROADMAP.md` і `DATABASE.md`:
- `users.materials_mode`, `orders.materials_mode`, `orders.share_bp` — видалити в 0.3.3.
- `master_charges` — архівувати та видалити після відповіді на Q-1.
- `expense_files` — не використовується.

**Рекомендація:** зробити це пріоритетом 0.3.3, щоб зменшити когнітивне навантаження.

### 2.4. Права і тести

- Перевірка прав у сервісах — добре.
- Повної автоматичної матриці «роль × ендпоінт» немає (`ROADMAP` 0.3.3).

**Пропозиція:** додати параметризований тест, який для кожного ендпоінта перевіряє очікуваний статус для `director`, `master`, аноніма і ключа Manager.

## 3. База даних і фінанси

### Сильні сторони
- Гроші в копійках, жодних float.
- Сторно + новий запис замість редагування на місці.
- `UNIQUE` + атомарні `UPDATE` для критичних дій.
- `ledger` тільки додавання (за домовленістю).

### Пропозиції
1. **Індекси.** Перевірити плани запитів фінансових звітів (особливо `analytics.py`) через `EXPLAIN QUERY PLAN`. Додати покриваючі індекси на часті запити, якщо потрібно.
2. **Партії / FEFO для складу** — вже в плані 0.4.0. Підтримую як наступний логічний крок після стабілізації 0.3.x.
3. **Архівація старих замовлень.** Після року роботи розглянути перенесення закритих змін старших N місяців у окрему таблицю-архів (якщо SQLite почне тормозити).
4. **Констрейнти на рівні БД.** Додати CHECK-констрейнти для `orders.amount = master_earning + materials_cost + salon_earning` (якщо SQLite дозволяє в поточній версії).

## 4. Безпека

Добрий рівень для одного салону. Конкретні покращення:

- **Хеші залежностей.** Зробити `pip-compile --generate-hashes` і перевірку вразливостей у CI (вже в плані).
- **Журнал входів.** Залишити 90 днів — добре. Розглянути алерт при незвичній кількості невдалих спроб з одної IP.
- **Секрети.** Переконатися, що `MDS_META_APP_SECRET` завжди заданий у production (вже підкреслено в README).
- **2FA.** Залишити обов'язковим для директорів у production.

## 5. Інтеграція з MDs Manager

Поточна модель (тільки читання + ack вебхуків) — правильна за каноном (D-5).

**Пропозиції:**
- Додати метрики черги `webhook_queue` (кількість pending, середній час обробки) у панель директора.
- Розглянути dead-letter для вебхуків, які перевищили N спроб.
- Документувати контракт `/api/ext/v1` як окремий API (OpenAPI чи хоча б окремий файл).

---

## 6. Фронтенд та UX

- Ванільний JS + `h()` — свідомий вибір ради простоти. Підтримую.
- Головна проблема — розмір `app.js`.

**Пропозиції:**
1. Розбити на модулі за вкладками.
2. Додати легкий збірник (напр. esbuild) лише для конкатенації, щоб зберегти простоту розробки.
3. Розглянути лінивий ліміт розміру бандла (зараз ~300 кБ стиснутого JS — ще ок, але слідкувати).

## 7. Операції та надійність

- Бекапи + шифрування + перевірка цілісності — добре.

## 9. Що не робити

- Не додавати мультитенантність.
- Не переписувати формулу `compute_split` без рішення директора і оновлення канону.
- Не зробляти фронтенд складнішим ради «сучасності» (залишити ванільний JS + модулі).
- Не давати Manager право писати в записи/замовлення (D-5).

## 10. Висновок

MDS Connect — добре спроєктована внутрішня система одного салону. Архітектурні рішення правильні, канон дотримується, фінансова модель чесна.
