# Фінансова модель MDS Connect (канон v0.3.0)

**Єдине джерело правди щодо грошей.** Суперечить код — міняється код. Інші правила (ролі, сповіщення,
інтеграції) і рішення директора D-1…D-8 — [CANON.md](CANON.md).
Діє для замовлень, закритих після релізу 0.3.0. Старі замовлення не перераховуються (D-2).
Стан коду на 11.11.2026 — `audit/07_FINANCIAL_FORMULAS.md` (там ще стара формула).

## 1. Гроші, ставки, способи оплати

- Гроші — **ціле число копійок** (`int`). Ніяких `float` чи `Decimal` у фінансових розрахунках.
- Ставки — **базисні пункти** (`5000` = 50 %). Ніяких дробових відсотків.
- Кожне фінансове значення розрізняє спосіб оплати: `orders.payment_method` ∈ `cash` | `card` | `transfer`.
  Звіти й каса спираються на це поле.
- Форматування для людей (`money.fmt`, `/ 100` у JS) — лише для показу, ніколи не в розрахунку.

## 2. Формула поділу (єдина)

```
master = (P × master_rate_bp) // 10000      # 50 % від ЦІНИ, округлення вниз
salon  = A − master − M
```

| Позначка | Що це | Звідки |
|---|---|---|
| `P` | ціна (до знижки), коп. | `orders.price_snapshot`, фіксується при закритті (D-3, Q-11) |
| `A` | фактично сплачено, коп. | `orders.amount` |
| `M` | реальна собівартість матеріалів **без націнки** | Σ `order_materials.unit_price_snapshot × qty` |
| `master_rate_bp` | ставка майстра | `orders.master_rate_bp`, за замовчуванням `5000` |

Код формули — **лише** `server/mds/services/finance.py::compute_split`. Інваріант: `A == master + M + salon`.

**Приклад 1 — без знижки:** P = 1000, A = 1000, M = 200 → майстер 500, салон 300, знижка 0.

**Приклад 2 — знижка 20 %:** P = 1000, A = 800, M = 200 → майстер **500** (знижка його не зачіпає),
салон 100, знижка 200 (за рахунок салону).

**Приклад 3 — салон у мінусі:** P = 1000, A = 600, M = 200 → майстер 500, салон **−100** →
критичне сповіщення обом директорам ([CANON.md](CANON.md) §5); **замовлення все одно закривається**.

Правила (не обертати):
- Майстер захищений від знижок: 50 % від `P`, не від `A`.
- Матеріали — за рахунок салону, **не** віднімаються до поділу.
- Знижка `P − A` — за рахунок салону.
- Округлення — на користь салону (`//`). Непарна копійка йде салону.
- Заробіток майстра не буває від'ємним (за побудовою `P ≥ 0`).

## 3. Поля замовлення

| Поле | Значення |
|---|---|
| `orders.price_snapshot` | `P`, коп., NOT NULL. Для старих замовлень при міграції = `amount` (знижка 0; D-2) |
| `orders.master_rate_bp` | ставка на момент закриття (з `users.master_rate_bp`, 5000) |
| `orders.amount` | `A` |
| `orders.materials_cost` | `M` (знімок) |
| `orders.master_earning`, `orders.salon_earning` | результат `compute_split` на момент закриття; звіти беруть **збережені** суми |
| `orders.payment_method` | `cash` / `card` / `transfer` |
| `orders.status` | `completed` / `unpaid` / `cancelled` / `refunded` (§8) |
| `orders.materials_not_entered` | позначка: закрито без матеріалів для послуги, що їх потребує |
| `orders.version` | оптимістичне блокування (§8) |
| `order_materials.unit_price_snapshot` | ціна одиниці на момент замовлення; пізніша зміна ціни не впливає |

Знижка **не зберігається**, а рахується при читанні: `price_snapshot − amount`.

## 5. Показники (вкладка «Фінанси», директор)

Порядок блоків згори вниз; перемикач періоду день / тиждень / місяць; кожен звіт можна сховати (дані рахуються).

| # | Показник | Формула |
|---|---|---|
| 1 | Реальна виручка | Σ `A` (лише `completed`; Q-8) |
| 1 | Знижки | Σ (`P − A`) |
| 2 | Частка майстрів (нараховано) | Σ `master_earning` |
| 2 | Частка салону (проміжна, до матеріалів) | Σ (`A − master`) |
| 2 | Матеріали | Σ `M` |
| 3 | **Валовий прибуток** | Σ (`A − master − M`) по послугах + маржа товарів (продаж − собівартість − бонус) − матеріали повернених замовлень. Натискання розкриває: складники; вигода від кращих закупівель ((середня ціна до приходу − ціна приходу) × кількість); матеріали за категоріями |
| 4 | Оренда, Комунальні, Реклама, Податки, Генератор, Інше | вручну + автоматично. Податки — нарахування ФОП (`tax_accruals`) за період; «Інше» = інше + обладнання + господарчі (Q-2) |
| 5 | **Чистий прибуток** | валовий − оренда − комунальні − реклама − податки − генератор − інше |
| 6 | Рентабельність | чистий / реальна виручка: ≥ 25 % 💚, 18–25 % 🟢, 14–18 % 🟡, 8–14 % 🟠, < 8 % 🔴 |
| 7 | Виплачено майстрам | підтверджені виплати |
| 7 | Борг майстрам | нараховано − виплачено (**без списань**) |
| 7 | Бонус за товари (накопичено) | Σ невиплачених `bonus_accruals`, окремий рядок |
| 8 | Неоплачені замовлення | кількість + сума; старші 3 днів підсвічені |

Готівка і картка показуються окремо в усіх звітах. Закупівля матеріалів і пального (категорії витрат) —
лише грошовий потік, у прибуток удруге не віднімається.

**«Аналітика» (директор):** рентабельність і шкала → рекомендації (`/api/analytics/recommend`) → кругова діаграма
«Куди йдуть гроші» → витрати → середній чек (загальний і по послугах).

**«Мої фінанси» (майстер):** поточна зміна (замовлення, заробіток, до виплати) → поточний місяць (заробіток,
виплачено, борг, бонус за товари) → стовпчики за 7 днів → топ-3 послуги місяця за кількістю
(`Стрижка: 15× → 1 500 ₴`) → історія, останні 20 записів.

## 6. Товари і бонус майстра

- Окремий тип складу: `products` (id, name, sku, barcode, cost_price_cents, sale_price_cents, markup_bp,
  category_id, stock_qty, active), продаж — `order_products` (order_id, product_id, qty, sale_price_snapshot_cents,
  master_bonus_cents).
- Бонус майстру — **10 % від ціни продажу**. Ціна фіксована з прайсу, при продажу не змінюється.
- Товар можна продати й **без послуги** — окреме замовлення, той самий потік.
- Додає майстер, поки зміна відкрита (під час або після закриття замовлення); після закриття зміни — лише директор.
- Виплата бонусів — **раз на місяць** (кнопка директора «Виплатити бонуси за товари»); дострокова — довільна виплата
  з тегом `product_bonus`.
- Повернення товару = нуль: повернення грошей + товар на склад + сторно бонусу. Якщо бонус уже виплачено —
  мінус з бонусу наступного місяця.

**Націнка** (`markup_bp`, за замовчуванням 10000 = 100 %) — інструмент директора, щоб порахувати `P`.
Вона **не** входить у `M` і не бере участі у формулі §2.

## 7. Фінансові сповіщення

Критичні: салон < 0 у замовленні; від'ємний баланс майстра. Важливе: зміна заробітку > 50 ₴; неоплачені > 3 днів.
Повний список, рівні й канали — [CANON.md](CANON.md) §5.

## 8. Життєвий цикл замовлення

Два окремі статуси, зв'язок 1 : 1. Замовлення створюється, коли запис закривається.

- `appointments.status` (календар): `pending → confirmed → in_progress → completed | cancelled | no_show`.
- `orders.status` (гроші): `completed | unpaid | cancelled | refunded`.

| Ситуація | Правило |
|---|---|
| `unpaid` | закрито, клієнт не заплатив; `amount` — сума, яку клієнт має сплатити. Заробіток майстра **нараховується** (ризик салону); у «Реальну виручку» не входить, доки не оплачено (Q-8). У списку «Неоплачені»; зміну закрити можна. Оплата пізніше: `POST /api/orders/{id}/mark-paid {method, amount}` → `completed` + аудит. Якщо зміну вже виплачено — різниця йде в наступну виплату |
| `refunded` | послуги й товари однаково: сторно в `ledger` + повернення товару на склад + сторно бонусу. Витрачені на послугу матеріали лишаються витратою салону (на склад не повертаються). Якщо майстру вже виплачено — баланс майстра стає від'ємним (критичне сповіщення) і переплата віднімається з наступної виплати |
| `cancelled` | анулювання помилково закритого замовлення: повне сторно, матеріали повертаються на склад, запис стає `cancelled` |
| `no_show` | лише в `appointments`; фінансових наслідків немає |
| Виправлення | директор, без обмеження в часі, **лише з причиною**: сторно старих сум + новий запис + `audit_log` (було / стало / хто / чому). Зміна вже виплачена → різниця автоматично в балансі майстра (`нараховано − виплачено`) і, отже, у наступній виплаті. Тег `correction_overpayment` — для ручного запису повернення переплати майстром |
| Скасування після виплати | так само: переплата — у наступну виплату |

**Оптимістичне блокування.** `appointments`, `orders`, `shifts`, `payouts`, `expenses` мають `version` (з 1).
Оновлення — `UPDATE … WHERE id = ? AND version = ?`; 0 рядків → **409** з поточним станом сутності в тілі;
UI показує «дані змінилися, оновіть».

**Ідемпотентність.** Клієнт надсилає `idempotency_key` при створенні замовлення. Той самий ключ → той самий
результат (той самий код відповіді). Інший ключ на вже закритий запис → **409**. Ключі — таблиця `idempotency_keys`
(`key`, `response_json`, `created_at`), видаляються через 30 днів (лише вона; фінансові записи — ніколи).

**Довільна виплата** (аванс / премія / бонус за товари / переплата) — прив'язана до **майстра**, не до зміни
(`payouts.shift_id` може бути порожнім), тег `advance | bonus | product_bonus | correction_overpayment`; зменшує борг.

**Звіт зміни** — знімок у момент закриття, після виправлень не змінюється (виправлення — нові записи в `ledger`).
Майстер бачить: свій заробіток, суму до виплати, замовлення, скасування. Директор — усе: виручку, майстра,
матеріали, знижки, салон.

## 9. Готівка при закритті зміни

```
taken_from_cash = min(earnings, cash_on_hand)
left_in_cash    = cash_on_hand − taken_from_cash
extra_pay       = max(0, earnings − taken_from_cash)    # директор доплачує на картку
```
`earnings` — заробіток майстра за зміну (без жодних списань; бонус за товари сюди не входить — він виплачується раз на місяць).
`cash_on_hand` — уся готівка зміни, разом із продажем товарів. `taken_from_cash` записується як виплата «з каси».

- 7 стрижок готівкою (3 500), 5 карткою (2 500), заробіток 3 000 → бере 3 000, у касі 500, доплата 0.
- Готівка 500, заробіток 1 500 → бере 500, у касі 0, директор доплачує 1 000.

## 10. Крайні випадки

| Випадок | Результат |
|---|---|
| Знижка більша за `P − master − M` | салон < 0 → сповіщення, замовлення закривається |
| `A = 0` (безкоштовно) | майстер 50 % від `P`, салон від'ємний → сповіщення |
| Повернення після виплати | переплата → наступна виплата; баланс може стати від'ємним → критичне сповіщення |
| `unpaid`, потім `mark-paid` з іншою сумою | виправлення з причиною (сторно + новий запис) |
| Повернення товару | нуль: гроші, склад і бонус сторнуються |
| Від'ємний залишок складу | дозволено, нічого не блокує → завдання на інвентаризацію |

## 11. Інваріанти (перевіряються тестами)

1. `amount == master_earning + materials_cost + salon_earning` для кожного замовлення.
2. `master_earning == (price_snapshot × master_rate_bp) // 10000` для замовлень 0.3.0+.
3. `master_earning ≥ 0`.
4. Σ рядків `ledger` по замовленню == поточним сумам замовлення.
5. Дашборд за період == Σ окремих замовлень і витрат за той самий період.
6. `ledger`, `audit_log`, `orders` — лише додавання; виправлення = сторно + новий запис.
7. Усі гроші — `int`.

## 12. Склад, комунальні, генератор (грошова частина)

- **Матеріали:** собівартість — **середня** (перераховується при приході). FEFO — пізніше, окремим проєктом (див. ROADMAP).
  Кожен рух — у журналі руху складу (дата, тип, позиція, кількість ±, ціна на момент, причина
  `receipt | consumption | sale | return | inventory | correction`, замовлення, користувач, примітка).
  Деталі — [DATABASE.md](DATABASE.md).
- **Електроенергія:** щомісяця `вартість = (поточний − попередній) × тариф` → підтвердження → одна витрата
  «Комунальні». Фактично сплачене — окреме поле, на прибуток не впливає (метод нарахування). Виправлення
  підтвердженого місяця — з причиною, сторно + новий запис.
- **Генератор:** вартість години = витрата (л/год) × ціна бензину + амортизація (константа налаштувань);
  знімок усіх параметрів при запуску; позначка «без світла» — лише для звіту; прогноз — лише інформаційний.
- **З майстрів нічого не списується** — салон покриває все.

## Застаріле (прибрати в 0.3.3)

`users.share_bp` → перейменовано на `users.master_rate_bp` (міграція з копіюванням даних).
`orders.master_rate_bp` для старих замовлень заповнюється з `orders.share_bp`.
`users.materials_mode`, `orders.materials_mode`, `orders.share_bp` лишаються в БД як історія старих замовлень;
код не читає їх для нових розрахунків. Колонки видаляються в 0.3.3.
